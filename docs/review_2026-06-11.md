# Code Review Report - 2026-06-11

Scope:

- Reviewed the non-vendored Python application code under `odoo_cli/`.
- Excluded `odoo_cli/_vendor/` and did not perform a line-by-line review of vendored Click.
- Used the current test suite and existing docs/tests as context, but this is still a targeted engineering review, not a formal verification pass.
- Focus was bugs, recovery edge cases, confusing behavior, and design smells in the new v1 implementation.

Verification observed before this report:

- `ruff check odoo_cli tests`
- `/opt/homebrew/bin/python3.13 -m unittest discover`

## Findings

### P1 - Old Git can make `odoo init` fail on an already-valid workspace

Files:

- `odoo_cli/commands/init.py`
- `odoo_cli/core/repositories.py`

`odoo init` calls `RepositoryService.clone_or_fetch()` for the default repositories before it checks whether the target worktree already exists and is valid.

`clone_or_fetch()` forces full-clone behavior for Git versions older than the blobless threshold. If the existing bare repository is partial/blobless, it then tries to replace the bare repo with a full clone. That replacement is intentionally refused when attached Git worktrees exist.

Consequence:

- A user with an already-working partial workspace and older Git can rerun `odoo init` and fail before the CLI notices that the existing worktree is valid and could have been left alone.

Suggested fix:

- Do not replace an existing partial bare repo during a generic fetch when checkout worktrees are attached.
- If replacement is unsafe, fetch and continue.
- Reserve full-reclone fallback for the moment a new checkout actually needs it and fails.
- Add a regression test for: old Git, partial `odoo.git`, valid attached `19.0/odoo`, rerun `odoo init`.

### P2 - Promisor retry reclones only `odoo`, even if another repository failed

Files:

- `odoo_cli/commands/init.py`
- `odoo_cli/core/worktrees.py`

When `create_full()` fails with a promisor/partial-clone error, `odoo init` always reclones `odoo.git` and retries.

However, `create_full()` checks out multiple repositories: `odoo`, `documentation`, and optional repositories when present. If `documentation.git` or an optional repository is the partial clone that fails during checkout, recloning only `odoo.git` fixes the wrong repository.

Consequence:

- The retry can fail again with the same error.
- The user sees a fallback path that sounds helpful but did not repair the actual failing repository.

Suggested fix:

- Have the worktree checkout layer surface the repository name/path that failed.
- Use the `git -C <repo>` argument from the failing command as a fallback if introducing a typed error is too much.
- Replace the specific failing repo, not always `odoo`.
- Add a regression test where `documentation.git` fails with a promisor error.

### P2 - Failed repo backfill can leave a broken checkout that future runs skip

Files:

- `odoo_cli/commands/init.py`
- `odoo_cli/core/worktrees.py`

For an existing valid worktree, `odoo init` now tries to add missing default repositories. This is good, but `WorktreeService.add_repository()` returns "already present" whenever the destination path exists.

If `git worktree add` fails after creating a partial destination, a future run will see the destination path and skip it as already present, even though it may be incomplete.

Consequence:

- A broken `19.0/documentation/` checkout can poison retries.
- The workspace can appear repaired while still missing a usable repository checkout.

Suggested fix:

- Add cleanup around `add_repository()` similar to `create_full()`.
- When the destination exists, validate that it is a real usable checkout before returning "already present".
- At minimum, for standard repos, check for a `.git` file/dir and maybe `git -C <dest> rev-parse --is-inside-work-tree`.
- Add a test where documentation backfill fails once and rerun repairs it.

### P2 - Linked worktree creation has no failure cleanup

File:

- `odoo_cli/core/worktrees.py`

`create_linked()` creates the target directory and symlinks standard repositories before checking out addon repositories. If addon checkout fails, the partial linked worktree remains on disk.

Consequence:

- Rerunning the same command hits "already exists".
- The user must manually remove the partial linked worktree.

Suggested fix:

- Wrap filesystem mutations in `create_linked()` with the same cleanup pattern used by `create_full()`.
- Remove the partial linked worktree and prune stale Git metadata on failure.
- Add a regression test where addon checkout fails after symlinks were created.

### P2 - `odoo test all` appears suspicious

Files:

- `odoo_cli/core/testing.py`
- `odoo_cli/core/odoo_bin.py`
- `docs/requirements.md`
- `README.md`

Docs say `odoo test all` means "every addon". The implementation resolves `all` to `["all"]`, then builds an odoo-bin command with `-i all`.

Unless Odoo has special handling for a module literally named `all`, this probably attempts to install a module called `all`, which is not the intended behavior.

Consequence:

- `odoo test all` may fail or test the wrong thing.

Suggested fix:

- Clarify desired semantics.
- Either enumerate installable addon module names from the resolved addons paths, or change the documented behavior.
- Add direct tests for `odoo test all`.

### P3 - Clone output can lie on older Git

Files:

- `odoo_cli/commands/init.py`
- `odoo_cli/commands/repo.py`
- `odoo_cli/core/repositories.py`

Command output says "blobless" or "full" based on the explicit user flag. The repository service can silently choose full clones on old Git.

Consequence:

- Users on old Git may see "Cloning odoo (blobless)..." even though the CLI chose a full clone.
- Not dangerous, but confusing during troubleshooting.

Suggested fix:

- Expose the effective clone strategy from `RepositoryService`, or add a small helper like `clone_mode(full_flag)`.
- Print "full (old Git does not use blobless)" when appropriate.

## Other Notes

- The clearer `odoo start` output is an improvement:

  ```text
  Starting Odoo: worktree=19.0 database=19.0
  URL: http://localhost:8069 (gevent: 8072)
  Ctrl-C to stop
  ```

- The `db_* = False`, `http_interface`, and `watchdog` warnings were intentionally not fixed in this pass. The plan is to address those through odoo-bin / v3 behavior rather than local migration logic.

- Existing tests are useful and fairly broad for a new implementation, but several recovery paths need failure-injection tests around partial filesystem state.

## Suggested Priority Order

1. Fix old-Git rerun behavior so valid existing workspaces are not blocked.
2. Make promisor retry repair the actual failing repository.
3. Add cleanup/validation for `add_repository()` backfills.
4. Add cleanup for linked worktree creation failures.
5. Clarify and fix `odoo test all`.
6. Make clone-mode output reflect the effective strategy.
